# 敌人替换与属性对齐 —— 方法论文档

> 本文说明"把普通遭遇的敌人换成另一个敌人、同时保留原地强度"这套做法的**原理、字段、
> 算法与验证方法**。配合 `docs/FINDINGS_ENCOUNTER.md`（数据事实）阅读。
> 工作目录：`D:\ps2\DDSAT2-rand-dsh`

---

## 1. 原理：这个游戏把"敌人"拆成两份数据

| 数据 | 存放位置 | 作用 |
|---|---|---|
| **敌人编号** | `ENCOUNT.TBL` 表1，记录内 `+10/+12/+14/+16/+18` | 决定"这场遭遇放什么怪" |
| **敌人属性** | `UNIT.TBL`，记录 `编号 + 127` | 决定等级/HP/MP/能力/技能/模型 |

所以**换外形和名字**只要改表1的编号；**换强度**要改 `UNIT.TBL` 记录。
两者一起改，就能做到"外形是 B、数值是 A"。

```
ENCOUNT 表1 记录 r:  [ ... 编号A ... ]  ──┐
                                          │  编号 → UNIT 记录 = 编号 + 127
UNIT.TBL 记录 127+A: 等级/HP/MP/能力/技能 ─┘
```

### 1.1 关键常量（**用错会整体错位一条记录**）

| 常量 | 值 | 说明 |
|---|---|---|
| `UNIT_BASE` | **127** | `UNIT.TBL` 记录 = `敌人编号 + 127` |
| 表1 记录起点 | `0x10` | 文件偏移；记录大小 40 |
| 编号槽位 | `+10 +12 +14 +16 +18` | u16，0 = 空槽 |
| UNIT 记录大小 | 76 | 文件头 16 字节 |

**`UNIT_BASE = 127` 的实测证据**：把所有遭遇记录改成编号 37，战斗面板显示
`LV52 / HP600 / MP368`，正好是 `UNIT.TBL` 记录 `164 = 37 + 127`。

## 2. 算法：1:1 双射 + 逐项对齐

### 2.1 建池

```
池 = { 被非剧情记录引用过的敌人编号 }
     ∩ { HP > 0 且 HP < 10000 }        # 排除占位/特殊单位（HP=32767）
     − { 只出现在剧情战阵容里的敌人 }   # Boss 专属不动
     − { 用户 ban 列表 }
```

### 2.2 双射置换

对池做一次随机 `shuffle`，得到 `mapping: 原编号 → 新编号`，
再修正自映射点（`perm[i] == pool[i]` 时与下一位交换），保证没有敌人保持原样。

### 2.3 改写遭遇记录

遍历表1 每条非剧情记录，把槽位里的编号按 `mapping` 替换。
空槽（0）和 `0xFFFF` 保持不动。

### 2.4 逐项对齐（**这一步决定"强度是否符合原地"**）

对每个 `source → target`：

```
rec    = 127 + target      # 游戏实际会读的记录
srcrec = 127 + source      # 被替换掉的那个敌人的原始记录
```

把 `rec` 的这些字段写成 **`srcrec` 的原始值**：

| 字段 | UNIT 偏移 | 做法 |
|---|---|---|
| 等级 | +53 | 直接复制 |
| HP 上限/当前 | +54 / +56 | 复制，两个必须同时写 |
| MP 上限/当前 | +58 / +60 | 复制，两个必须同时写 |
| 五项能力 | +64..+68 | 见 §2.5 |
| 技能列表 | +0..+9, +72/+74 | 复制（5+2 个 u16） |

> source 的数值必须取自 **boot 时的原始 UNIT.TBL 快照**，
> 否则两次 swap 互相引用会串味。

### 2.5 五项能力：两种模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `stats_mode = "copy"`（默认，推荐） | 直接把 source 的五项能力**原样复制** | 想完全保留原地强度分布 |
| `stats_mode = "scale"` | 按 `target能力总和 / 原总和` 等比缩放，再四舍五入、裁到 1..99 | 想保留新敌人自己的"性格"（力型/魔型） |

`scale` 模式只保证**总和**接近，个体会有 ±几点误差；
`copy` 模式保证**逐项完全一致**。

### 2.6 被 ban 的敌人怎么处理

- 从池里移除 ⇒ 不会再被换进任何位置；
- 但它原来占的**遭遇记录**必须仍然存在，否则那条刷怪点会空掉或退化成别的怪。
  做法：**把该记录整条改写成"同场景的另一条遭遇"**：
  - 优先用**同一个表1 块**里的干净记录（同场景、同等级段、同数量级）；
  - 整块都是 ban 的时候，退而选**最近的**干净记录，并优先挑**相同敌人数**的那条；
  - 写进去的是 donor 记录**经过置换后**的编号（所以在 pass 3 才落地）。
- **由用户决定 ban 谁**，程序只负责执行：

```bash
python dds2_randomizer.py --iso DDSAGA2.iso --out out.iso --ban-file bans/enemies.json
python dds2_randomizer.py ... --ban 120,121,122
```

ban 文件格式（json 或纯文本都可以，`#` 为注释）：
```json
{ "ban": [120, 121, 122] }
```

### 2.7 怎么知道哪个 id 是哪个敌人

```bash
python tools/enemy_info.py --all --used-only            # 一览：id/名字/等级/HP/MP/能力/模型/出现记录
python tools/enemy_info.py 76 75 41                     # 看某几个
python tools/enemy_info.py --all --used-only --sort level
python tools/enemy_info.py --all --used-only --hp 1 999 # 只看 HP 1..999
python tools/enemy_info.py --write-ban bans/enemies.json 120 121
python tools/enemy_info.py --write-names-template bans/enemy_names.json
```

> **关于名字**：敌人名存在消息表里，用的是中文补丁的自定义字形编码，目前还没解码；
> ISO 里也搜不到明文名字表。所以名字走 **`bans/enemy_names.json`** 这个由用户维护的映射：
> `{"76": "アルプ", "75": "カハク"}`。填了名字工具就显示，没填显示 `?`；
> 其余字段（等级/HP/MP/能力/模型/出现记录）全部来自游戏数据。
>
> 判别"人类兵"的实用办法：用 `--sort hp` 看低等级+低 HP 的那一批（人类兵通常 HP 很低、
> 技能很少），进游戏对一下外形，再把 id 填进 ban 文件。

### 2.8 中文文本编码（解码进展）

游戏文本（MSG1 条目的 text 载荷）**不是** GBK / Shift-JIS / UTF-8 任何一种，
而是补丁自带的**自定义字形编码**。已确认的事实：

| 观察 | 结论 |
|---|---|
| 载荷开头 `f2 08 ff ff f2 06 02 ff` | 控制序列（字体/参数），可跳过 |
| `82 89` 出现 905 次、几乎总在载荷末尾 | 换行 / 结束符 |
| `ff ff` 出现 1191 次（= MSG.TBL 条目数） | 每条目一次，分隔/终止符 |
| `80 80` 出现 187 次 | 空格类填充字形 |
| 首字节（lead）分布 | **只在 0x80..0x99**（另加控制用 0xf1/0xf2/0xff） |
| 尾字节（trail） | 0x02..0xff，较分散 |

**已对照出的字形码**（用 item_001..item_009 "同一物品只差一个字"的载荷做
序列对齐得到）：

| 字形码 | 字 | 依据 |
|---|---|---|
| `81 8b` | 功 | item_001 的"功"在改版里变成了"属"（`84 fe`） |
| `81 90` | 体 | item_002 的"体"在改版里变成了"力"（`80 ea`） |
| `80 91` | 命 | 只在 item_001 系列出现，对应"勾玉(命)"的"命" |
| `80 95` | 素 | item_001/002 互换时与"命"一起移动，是"素" |
| `80 a8`（旧标 `80 88`） | 力的属性槽 | … |
| `80 ad` | 运 | 改版 item_009 把"运"换成"速"（`80 e3`） |

> 上表里带"依据"的行是**序列对齐确认**的；其余标注是候选，需要再用别的条目验证。

具体的载荷结构（item_001 系列）：

```
82 f7 82 fd 81 90 82 f1 83 fe 81 ff   ← 第一段：勾玉的固定部分
f1 0f                                   ← 控制码（分段）
80 95 80 91 86 c0                       ← "命"相关的可变部分
80 a8 80 b0                             ← "(" ")"
82 89                                   ← 换行
0a 00                                   ← 结束
```

**已知的控制/结构码**：`f1 0f`（分段）、`82 89`（换行/结束，905 次）、
`ff ff`（条目终止，每个 MSG 条目一次）、`80 80`（空白填充）。

`/font/name_ent.fnt` 头部是 24×24 点阵（`u32@4` 指向文件偏移 `0x99b1a` 的数据块），
`0x20` 起有一张疑似**字形索引表**（前 16 项 `10 10 10 80 / 20 20 20 80 / …`，
`0x68` 起是 `[??][??]` 形式的小值对）。**这张表与字形码的对应关系还没建立**，
所以完整的"字形码 → 汉字"表尚未解出。

**结论**：目前只有少量常用字对照，`bans/enemy_names.json` 仍需人工补全。
若要自动化，下一步应做**序列对齐**：拿同一物品/技能的多条载荷互相对齐，
把"唯一变化的字形码"与"已知的中文词"配对，逐步攒出完整码表。
（探查脚本：`scratch/z_cn*.py`、`scratch/z_fnt*.py`。）

## 3. 不变量（改完必须成立）

1. `ENCOUNT.TBL` 与 `UNIT.TBL` 的**文件长度不变**（原地覆盖，不 relocate）；
2. 表1 的 0 号记录、剧情战记录（Boss）不被普通遭遇随机化改动；
3. 每条非空遭遇记录，其编号在 `UNIT.TBL` 里都指向一个 `HP > 0` 的可用记录；
4. 对每个被替换的槽位，`UNIT[127 + 新编号]` 的 **等级/HP/MP** 等于
   `原 UNIT[127 + 原编号]`；
5. 被 ban 的编号不出现在任何遭遇记录里，也不在任何 `UNIT` 重调目标里。

## 6. 敌人 ID ↔ 属性 对照表（每次构建自动生成）

构建 ISO 时会在输出旁边自动写两份对照表（`--no-enemy-table` 可关闭）：

```
DDS2_random_v18_full_enemies.txt
DDS2_random_v18_full_enemies.csv
```

格式（数值全部是**这个 ISO 里**的最终值，所以随机化后的强度也能对上）：

```
id   lv   HP      MP      STR MAG VIT AGI LUK  skills        records
5    9    76      96      7   10  15  9   9    83,337,19,22  22 23 24 49
```

- `id` = 敌人编号（ENCOUNT 里的编号，游戏里按 `id + 127` 取 UNIT 记录）
- 打怪时用**等级 / HP / MP** 就能反查是哪个 id（分析技能看到的数值就是这个 HP/MP）
- `records` = 该 id 出现在哪些遭遇记录（空 = 只在剧情/特殊战里）

> 提示：**id ≥ 258 的大多是 Boss / 精英战专属**，拿它们当锚点最省事。

## 7. 让 Boss / 精英敌人可以被分析（**已实现 + 已实机验证**）

需求：游戏里 Boss / 剧情 / 特殊敌人被分析时**不显示** HP / MP / 技能（显示成「？」）。

> **实机验证结果（2026-10-06）**：`--reveal-enemies` 的代码补丁生效，
> 分析 Boss 时**等级 / HP / MP 显示真值**。
> **已知边界：技能那一栏仍然是「？」** —— 见 §7.7。

### 7.1 诊断：13 个守卫，测两个静态开关（**或**关系）

分析面板的每一行由一个"行绘制函数"填值，表在 VA `0x415650`：

| 行函数 | 作用 |
|---|---|
| `0x1B8E68` | 第 1 行（HP），有「？」分支 |
| `0x1B8F28` | 无「？」分支 |
| `0x1B8FB0` `0x1B9018` `0x1B90E0` `0x1B91E8` `0x1B9308` | 其余各行，都有「？」分支 |

其中 **6 行**会在下面任一条件成立时跳到占位符绘制函数 `0x1B8930`（画「？」）。
判断点在 `0x1B8E94` 一带：

```
0x1b8e7c  v1 = battlework->[672]        ; 遭遇记录索引
0x1b8e84  v0 = v1 * 40 + ENCOUNT.TBL    ; gp-20588 是 ENCOUNT.TBL 指针
0x1b8e94  v1 = *(u16*)(v0 + 32)
0x1b8e98  v1 &= 1
0x1b8ea0  if (v1) -> 0x1b8930           ; 「？」占位符

0x1b8ea8  a1 = state->[4]               ; 当前单位
0x1b8eb0  v1 = *(u16*)(a1 + 292)        ; 单位 id
0x1b8ec8  v0 = *(gp-20612) + v1 * 76    ; 战斗单位模板表
0x1b8ecc  v1 = *(u32*)(v0 + 0)          ; 模板 +0
0x1b8ed0  v1 &= 0x800
0x1b8ed4  if (v1) -> 0x1b8930

0x1b8edc  v0 = *(u8*)(v0 + 22)          ; 模板 +22
0x1b8ee0  if (v0) -> 0x1b8930
```

**战斗单位模板表**（指针在 `gp-20612`，76 字节一条，按单位 id 索引）的头 28 字节
就是 `UNIT.TBL` 记录的**尾部**：

```
template[i][0..27] == UNIT.TBL[127 + i][48..75]
```

所以在静态文件里，两个开关是：

| 开关 | 位置 | Boss 上的取值 |
|---|---|---|
| 遭遇级「隐藏资料」 | `ENCOUNT.TBL` 表1 记录 `+32` 的 **bit 0** | 42 条剧情/Boss 遭遇全为 1 |
| 单位类别字节 | `UNIT.TBL` 记录 `+70` | 79 条 Boss/精英全为 `0xFF` |

（第三个条件对应 `UNIT.TBL` 记录 `+49` 的 bit 3，实测 896 条里一条都没有置位，可以不管。）

**两者是「或」关系** —— 只要有一个成立就显示「？」。这就是之前"只清 `+70`"
或"只清 ENCOUNT `+32`"都无效的原因：**必须两个一起清**。

### 7.2 存档证据（定位过程）

用户提供的 Boss 战即时存档（`SLPM-65795 (00C2973C).00/01.p2s`）里：
战斗工作区 `+672 = 768`，而 `ENCOUNT.TBL` 记录 768 是
`000000000100000000003b0101013b0100000000000000000000000000000000dd0003000d0d0000`，
`+32 = 0x00DD`，bit 0 = 1 —— 正是被隐藏的那一场。
该存档里战斗单位模板 `[315]`、`[257]` 的 `+22` 都是 `0xFF`（= `UNIT.TBL[442/384][70]`），
两个条件同时成立。

全表统计：`+32` bit 0 置位的 42 条记录，出场的敌人 id 全部是 `+70 == 0xFF` 的 Boss 单位。

### 7.3 第一次实现（改数据）**已验证会导致 Boss 战加载卡死**

按 7.1 的结论，第一版直接清数据：

* `UNIT.TBL` 每条 HP 正常的记录（127..895）的 `+70` → 0（79 条）；
* `ENCOUNT.TBL` 表1 全部 1024 条记录的 `+32` → 清掉 bit 0（42 条）。

**实机结果：进入 Boss 战时卡在加载，进不了战斗。** 原因：这两个字节不只是"隐藏资料"
的开关，战斗逻辑也在用 —— 尤其 `+70` 是**单位类别**，Boss 上的 `0xFF` 是"无类别"哨兵值，
改成 `0` 之后战斗流程会走另一条分支（`0x1AB9C8` 的调用点会 `sltiu n,8` + 跳转表
`0x414F10` 分派），进而卡死。

数据层因此**放弃**：`--reveal-all-bytes` / `--patch-unit-bytes` 两个旧探针开关已删除，
`Config.reveal_all_bytes` / `unit_patch_bytes` 保留但不再使用。

### 7.4 最终实现（改代码，不碰数据）

那 13 个"跳到占位符"的判断分支全都是同一形状：

```
bnel <reg>, zero, <jal 0x1B8930 的地址>
```

`bnel` 是 "likely" 形式：不跳转时会**作废延迟槽**。把比较用的 `rs` 寄存器换成 `$zero`：

```
bnel zero, zero, <同一个地址>
```

条件 `0 != 0` 恒为假 ⇒ 永不跳转，且延迟槽照样作废 —— 与"标志位没置位"完全等价，
其余指令流一个字节都不动。**只改这 13 个字的 `rs` 字段。**

13 个站点（VA）：

```
0x1B8EA0  0x1B8ED4  0x1B8EE0          第 1 行（HP）
0x1B903C  0x1B9070  0x1B907C          共用尾部 0x1B90D0
0x1B9104  0x1B9138  0x1B9144          尾部 0x1B91D8
0x1B9240  0x1B924C                    尾部 0x1B9274
0x1B9360  0x1B936C                    尾部 0x1B93CC
```

模块 `src/ddstool/analyse.py` 每次运行都**重新扫描** `0x1B8E00..0x1B9400` 找这些分支
（不是硬编码地址），自检断言必须正好 13 条、形状是 `bnel reg,zero,<占位符>`。

优点：

* `UNIT.TBL` / `ENCOUNT.TBL` **一个字节都不改**，战斗逻辑完全不受影响；
* 只改 `SLPM_657.95` 里 13 个字的 `rs` 字段，ELF 大小不变、ISO 布局不变。

自检断言：`reveal: 13 analyse guard(s) found (shape ok)`、
`reveal: ELF size unchanged`、`reveal: only the 13 guard words changed (0 stray)`、
`reveal: game data untouched (UNIT/ENCOUNT not rewritten)`。

## 8. 敌人 AI 行动表（AICALC.TBL）

敌人换上新的技能组后，**AI 出招表还指向旧技能**，所以要一起改。

### 8.1 结构：文件里其实是两样东西，互不相干

`/battle/AICALC.TBL`（375,776 字节）由前后两段拼成。

#### （a）`0x10 .. 0x21a4c` —— 普通敌人的"平坦行动表"

395 条记录 × **348 字节**：

| 记录内偏移 | 内容 |
|---|---|
| `+0 .. +51` | 记录头；没用到的半边填常数 `0x0808`（就是它让记录形状在 hex dump 里一眼可见） |
| `+52 .. +339` | **36 条行动项**，每条 8 字节 |
| `+340 .. +347` | 记录尾字段，**不是行动** |

行动项：

```
+0            +2           +4          +6
[u16 权重] [u16 技能ID] [u16 条件A] [u16 条件B]
```

所以第 `j` 条行动的技能 ID 在 `记录起点 + 52 + 8*j + 2`。

- 实测权重只有 `0, 5, 10, 15, 20, 25, 30, 35, 40, 50, 70, 100`；
- 条件 A 是定点血量比：`0x3333` = 0.2、`0x6666` = 0.4、`0x999A` = 0.6、`0xCCCD` = 0.8；
- 条件 B 是条件参数，取值 `128 / 64 / 20 / 10 …` —— **正好落在技能 ID 区间内**，
  这就是"扫描全文件每一个 u16"必然改坏表的原因。

**尾字段不是第 37 条行动**：它的第 2 个 u16 落在 1..600 的次数是 **33**，
而左右邻居分别是 **1** 和 **0**；它的第 1 个 u16 几乎从不为 0。当行动处理会改坏它。

**记录 k 属于 UNIT.TBL 记录 k + 128**（即敌人编号 k + 1）。证据：

| 配对方式 | 平均覆盖率 |
|---|---|
| AI 记录 k ↔ UNIT 记录 **k+128** | **56.3%** |
| AI 记录 k ↔ UNIT 记录 k+127 | 4.7% |
| AI 记录 k ↔ UNIT 记录 k+129 | 4.7% |

覆盖率在 k 上**不漂移**（k=0..49 是 53.8%，k=300..349 是 63.3%），
这也反过来确认了 **348 字节**的记录长度：344 / 346 / 350 / 352 全都掉到 8~30%。

#### （b）`0x21a4c` 之后 —— 两个 FlowScript 模块（magic `FLW0`）

第一个放具名战斗 AI（`ai_test`、`AI_KARMA_M`、`AI_VETARA`、`AI_ABADON`、
`AI_KAKUHEKI_*` …，共 89 个），第二个放 `calc_*` 辅助函数。

```
+0   char[4]  "FLW0"
+4   u32      reserved
+8   u32      section count
+12  u32      field14
+16  u16[4]   reserved
+24  段描述符，每个 16 字节：[u32 id][u32 unitSize][u32 unitCount][u32 startOffset]
```

`id`：0 = `.label.proc`、1 = `.label.jump`、2 = `.text`、3 = `.data.msg`、4 = `.data.str`；
`startOffset` 相对 `FLW0` magic。MSG1 块住在 `id = 3` 的段里，段的范围
`[startOffset, startOffset + unitSize × unitCount)` 是这块文本真正的边界（见 §11.13.2）。

指令是 u32 小端 `[u16 opcode][u16 operand]`；带整字操作数的 opcode
（0 PUSHI、1 PUSHF、10 JUMP、11 CALL、28 IF、34 PUSHSTR）会再吃掉一个字。

AI 选招的形态是：

```
PUSHIS <技能ID>        (opcode 29，操作数就是那个 u16)
COMM   51              AI_ACT_SKILL
```

按脚本编译器的实参顺序，被压栈的实参就在 `COMM` 的**前一个字**。
原版文件里 **849 个 `AI_ACT_SKILL` 调用点无一例外都是这个形状**；
`AI_ACT_SKILL_PARAM`（库索引 226）同形，另有 4 处。

### 8.2 做法：只改上面这两个地方

交换敌人时同时建立一张 `旧技能ID → 新技能ID` 的表：

- 对每个 `source → target`：`target` 的**交换前**技能列表 = 旧，**交换后** = `source` 的技能；
- 两个列表**按槽位一一配对**，得到 `old[i] → new[i]`；

  > ⚠️ **不能先滤掉 0**。`_retune_unit` 是整表复制（`set_skills(rec, srctable.skills(srcrec))`），
  > 所以位置 `i` 现在装的就是 source 的第 `i` 个技能。若先把两边的 0 滤掉再 zip，
  > 一侧为空、另一侧非空时两个列表就会错位，映射整体串位。

- 然后分两处替换，**其余一个字节不动**：

  | 位置 | 用哪张表 | 为什么 |
  |---|---|---|
  | 平坦行动表 | **每个单位用自己那张表** | 记录 k 明确属于 UNIT 记录 k+128，所以能精确到单位，一个技能 ID 被两个单位共用也不会串 |
  | FlowScript（853 个 `PUSHIS`） | 合并后的全局表 | FLW0 的 AI 过程无法归属到具体单位，只能全局 |

  按单位改是**必须的**：若对整张平坦表套用全局表，凡是"技能 ID 恰好等于某个被替换技能"
  **但自己并没有被交换**的单位也会被一起改掉（实测有 345 处这种误伤）。

`selftest.py` 里对这两条做了硬校验：

```
AICALC skill operand sites (2513)                     OK
AICALC only skill ids touched (903 changed, 0 stray)  OK
AICALC every change follows the remap                 OK
AICALC FlowScript sites remapped (358)                OK
```

`0 stray` 是关键：逐 **字节** 比对原版与产物，**每一个变化的字节都落在某个允许的
技能操作数 u16 之内**。

```bash
python dds2_randomizer.py --iso DDSAGA2.iso --out out.iso            # 默认开启
python dds2_randomizer.py ... --no-ai-remap                          # 关掉
```

### 8.4 注意

- 平坦表里约 **47%** 的技能引用**不在**该单位的 5 个技能槽里
  （技能槽是 `+0/+2/+4/+6/+8`；逐槽位覆盖分析里其它偏移最多再贡献 2%）。
  这些 ID 不在重映射表里，**保持原样** —— 这是预期行为，多半是它本来就用不出的招式。
- 重映射是**全局**的。一个技能 ID 若同时属于多个单位，只能跟随其中一个：
  本次构建有 36 个这样的 ID，日志会把它报出来。
- `+72/+74` **不是**技能（逐槽位覆盖分析里只贡献 1.3%，接近噪声），
  因此不进重映射表；但 `_retune_unit` 仍会按原样一起复制它们。
- `--no-ai-remap` 可以随时关掉这一功能，其余随机化不受影响。

### 8.5 走过的弯路（保留结论，避免重犯）

| 做法 | 结果 |
|---|---|
| 扫描全文件每个 4 字节块，`s in remap` 就改 | 改 8967 处，**启动 TLB Miss 崩溃** |
| 加 `1 <= w <= 9999`、`1 <= s <= 600` 过滤 | 改 8583 处，**仍崩溃** |
| 再收紧到"值必须是 UNIT 里真实存在的技能 ID 且 `w <= 999`" | 改 8570 处，**仍崩溃** |
| **只改平坦表 36 × 395 个技能槽 + 853 个 `PUSHIS` 操作数** | **970 处，0 处越界** |

对照实测：`DDS2_diag_noai.iso`（完整随机化、不动 AICALC）**能启动**，
`DDS2_random_v19_full.iso`（全文件盲改）**启动崩溃** ⇒ 崩溃确实来自 AICALC 改动。

前三种之所以失败，是因为它们扫的是**整个文件**：

- FLW0 的**标签名**和**字符串表**会被当成技能 ID；
- 行动项旁边的**条件参数**取值 `128 / 64 / 20 / 10`，**正好和技能 ID 撞区间**，
  按数值范围根本无法区分。

结构定位清楚之后，这两个问题自然消失 —— 这也是为什么现在能给出
"0 处越界"这种强度的验证。

> **做法一句话**：`.LB` 里 `BF` 成员解压 → 把每条消息按「控制码 / 纯文本片段」切开 →
> 只把**纯文本片段**按字节长度丢进全游戏随机池互换（优先跨文件）→ 控制码原样留在原位 →
> 重新压缩回原槽位。
>
> ⚠️ 早期几节（11.3 / 11.6 ~ 11.10）记录的是**已经被推翻的探索路径**，保留作为历史；
> 结论以 11.11 起为准。

### 11.1 台词存在哪

全游戏只有 **160 个可解析的 MSG1 表**：

| 扩展名 | classify() | 文件数 | 条目数 | 说明 |
|---|---|---|---|---|
| `.PM1` | `cg` | 79 | 1379 | 过场动画字幕 —— **散装文件，游戏直接读** |
| `.bf` | `ingame` | 64 | 3220 | 场内 + 事件对话（含 NPC 台词）|
| `.bmd` / `.bf` / `.TBL` | 未覆盖 | 17 | 710 | 战斗系统、商店、终端、曼陀罗 —— 有意不动 |

NPC 对话确实在 `/fld/f/fNNN/fNNN.bf` 的 MSG1 里，条目名形如 `npc07_005_001_01`、
`roald_025_054_01`、`MR_JOHNNY`、`FREE_KIDS_1`，长度 30~460 字节。

### 11.2 ⚠️ 关键：场内 `.bf` 是"散装副本"，游戏读的是 `.LB` 里的压缩版

**这是 NPC 台词改了却毫无效果的根本原因。**

`/fld/f/fNNN/fNNN_000.LB` 是一个**按块打包的容器**：

```
[01 01 块号 00] [u32 压缩后大小] [char[4] 块名] [u32 解压后大小] [压缩数据…]
```

| 块号 | 块名 | 解压后大小 | 与散装文件的关系 |
|---|---|---|---|
| 1 | `INF` | 15232 | = `F004.INF` |
| 2 | `NPL` | 512 | = `F004.NPL` |
| 3 | `SKY` | 57344 | = `F004.SKY` |
| 4 | `WAP` | 27904 | = `F004.WAP` |
| **5** | **`BF`** | **107759** | **= `f004.bf`** |
| 6 | `AMB` | 39990 | = `f004.amb` |

块大小与同目录散装文件**逐一对应**，`BF` 块就是场内脚本。1014 个 `.LB` 里
**29 个**带 `BF` 块，正好覆盖那 21+ 个有 NPC 台词的场内 `f00N.bf`。

⇒ **游戏读的是 `.LB` 里的压缩副本**；散装 `f00N.bf` 改了也没用
（这也解释了为什么 CG 字幕会变、NPC 台词不会 —— `.PM1` 没有打包，是散装文件）。

**顺带排除的其它候选**：`.LB` 里的 `MSG1` 字样 22 处**全是误命中**（真表头后必须跟
4 个零字节）；`.smg`（2272 个）是 `/sound/*.SMG` MIDI；`.f1`/`.f2` 的 magic 是
`FLD1`/`FLD2`（地图数据）。

### 11.3 块内压缩：容器已解，编码部分解出（**未完成**）

**容器结构已经完全确认**（逐字节核对，见 11.2 的表格）：

```
+0   u8 u8 块号 u8=0     固定 01 01 NN 00
+4   u32                压缩后（存储）大小
+8   char[4]            块名，如 "INF\0" / "BF\0\0"
+12  u32                解压后大小
+16  …                  压缩数据，长度 = +4 那个字段
```

对齐到 16 字节边界后是下一个块头；`AMB` 通常是最后一个块，它的数据一直顶到文件末尾。

**块内编码：部分解出。** 以 `F001.INF` 为例（111 字节 → 15232 字节）：

```
压缩: 25 08 | 30 31 65 76 65 5f 30 31 | ...
明文: 00 00 00 00 00 30 31 65 76 65 5f 30 31 ...
      └─ 5 个 0 ──┘ └──── 8 个字面量 ───┘
```

所以 token 是 **2 字节 + 若干字面量**：

- 第 2 字节 = **字面量个数**（这里是 8，正好是 `"01eve_01"`）；
- 第 1 字节的低 4 位 = **回拷长度**（这里是 5，正好 5 个 0）；
- 第 1 字节的高 4 位 = 与**回拷距离**有关（多数 token 是 `2`，也有 `6`）。

同样的形状在 `BF` 块开头完全吻合：

```
明文: 00 00 00 00 f9 3f 00 00 46 4c 57 30 00 00
压缩: 24 02 f9 3f 22 04 46 4c 57 30 24 01 05 ...
      └4个0┘ └f9 3f┘ └2个0┘ └─ FLW0 ─┘ └1个0┘
```

（`46 4c 57 30` = `"FLW0"`，即脚本 magic —— 再次确认 `BF` 块就是 `.bf` 的内容。）

**卡住的地方**：回拷**距离**的编码规则还没确定。上面这种"距离 = 常数/高 4 位"的几种猜测都只能解对开头几百字节，
继续下去就错位；`NPL` 块（明文是 `73 73 73 33 33 33 f0 00` 重复，28 字节 → 512 字节）
更是完全对不上，说明距离的编码方式不止一种或有转义。

试过并**失败**的：仓库里的 LZO1X 解码器、zlib、raw deflate、
以及 6×6×5 = 180 种"匹配长度/距离/字面量个数"取法的穷举（要求在 `F001.INF` 前 64 字节全对）。

**结论：场内 / NPC 台词随机化暂时无法实现。** 需要先把块内编码完全解出，
再实现"等长回写"（解压 → 改文本 → 重新压到不超过原存储大小 → 原地写回）。
在此之前，程序对散装 `.bf` 的改动是**无效的**（但无害）。

### 11.4 CG 字幕：**只做等长互换**（当前定稿做法）

> **结论一句话：CG 字幕只在"字节长度完全相同"的两条之间互换，不做任何补位或截断。**

**字幕所在的文件**（这是唯一真正生效的文本位置）：

| 路径 | 说明 |
|---|---|
| `/event/eNNN/eNNN/eNNN_NNN/E*_NNN.PM1` | 过场动画文件，共 **79 个** |
| 其中真正放字幕的 | 文件里的 **MSG1 表**（`PMD1` 容器的 chunk id=6），共 **1374 条**条目 |

`.PM1` 是 `PMD1` 容器（`[u32 id][u32 size][u32 ?][u32 offset]` × N 的块表，
块名有 `TBN/TXP/FLD1/FLD2` 和文件名 `eNNN_NNN.msg`）。
**MSG1 表就是字幕本体**，没有单独的 `.msg` 块。

条目结构（逐字节核对）：

```
+0     char[16] 名字（如 XSER2010）
+16    u8[8]    reserved（全 0）
+24    u16      行数 n
+26    u16      0xffff
+28    u32      语音偏移[n]     ← 相对本文件的偏移
+28+4n u32      文本长度
+32+4n u8[]     文本（中文补丁的自定义双字节字形编码）
```

**做法**：

1. 把**全部 79 个 `.PM1` 的 1374 条条目放进同一个池子**，按"文本长度"分组；
2. 每一组内打乱后两两配对 —— 所以一条字幕可以来自**任何一段过场**（实测 674 对里
   654 对是跨文件的）；
3. **只把文本载荷整段搬过去，字节数完全相同**。

**绝不改动的东西**（每一条都是实测逼出来的，见 11.5）：

```
名字 / reserved / 行数 / `length` 字段 / `u32 @+28` 语音数组   ——  全部原样
```

**覆盖率**（seed 12345）：**1254 / 1374** 条字幕发生变化。
理论上限是 1348 条（98.1%），差额来自"两条台词文本恰好完全一样"和每组奇数的落单。

### 11.5 为什么本轮方案只能是等长互换（实测证据）

| 版本 | 做法 | 结果 |
|---|---|---|
| v22 | 整条条目重建（连 `lines`/语音/长度一起搬） | ❌ **CG 字幕全部消失 + 偶发卡死** |
| v23 | 同文件 + 等长互换（语音也换） | ⚠️ 部分被替换；**跨文件**那批才看得见变化 |
| v24 | 长度补全（补 `80 80` / 截断）+ 换语音 | ❌ **绝大部分字幕退回原句** |
| v25 | 长度补全（补位/截断），不动语音 | ❌ 字幕"**闪一下就消失**"，且只在同场景内打散 |
| **v26** | **全局等长互换，不动语音** | ✅ 1254 条跨场景随机，无闪屏 |

三条被实测否掉的规则：

1. **`length` 字段不能改** —— 改了之后 CG 字幕整体消失（v22/v24）；
2. **`u32 @+28` 语音数组不能动** —— 一动，该条字幕就退回原文
   （v24 换了 1330 条，玩家报告"绝大部分没被随机"；v23 只换了 630 条，
   恰好就是那批看起来没变的）；
3. **不能补位、不能截断** —— 短文本补空白字形会让字幕"闪一下就消失"（v25）。

另外，"先在同一文件内配对"是错的：那只是把一段过场内部重新排序，
看起来像什么都没发生（v25 报告）—— 必须**全局配对**。

### 11.6 绕过压缩：把 `BF` 成员改成"未压缩存储"（当前方案，待实测）

**不再尝试破解块内压缩算法**，改用容器自带的标志位。

`.LB` 的块头就是 Atlus 的"通用头"（见
[Amicitia Wiki: BF](https://amicitia.miraheze.org/wiki/BF)）：

```
+0   u8     文件类型
+1   u8     压缩标志   ← 0 = 未压缩，1 = 压缩
+2   u16    成员编号
+4   u32    存储大小
+8   char[4] 成员名（"INF\0" / "BF\0\0" / "AMB\0" …）
+12  u32    解压后大小
```

**关键：块头里没有偏移字段。** 读取方是顺序遍历的 —— 读完一个头就跳过
`stored` 个字节找下一个头。所以**把某个块变长，后面的块自然顺移**，不需要修正任何偏移。

于是做法是：

1. 读出 `BF` 成员，把它的 **`compflag` 置 0**，`stored` 改为 `unpacked`，
   数据直接放**未压缩**的 `.bf` 内容；
2. 容器随之变长 —— 这需要给文件腾地方。

**空间从哪来**：`DDS3.IMG` 内部只有 7.16 MB 空闲，而且**最大连续块只有 2046 字节**
（全是文件之间的扇区对齐缝隙），根本放不下变大的文件。但是：

```
DDS3.IMG      结束于 0x57b5f800 (1.47 GB)
ZZZ50MB.DAT   开始于 0x10c40f800 (4.49 GB)   ← 中间约 3 GB 完全没用
```

所以 `Game.alloc_extend()` 把变大的文件追加到 `DDS3.IMG` 末尾，扩大 IMG，
并在 `save_ddt()` 里同步改写 ISO9660 中 `DDS3.IMG` 的记录大小（LE+BE 两份）。

22 个带 NPC 台词的场内容器一共增长约 **1.4 MB**，远小于那 3 GB。

### 11.7 探针：`DDS2_probe_lb.iso`（内容一个字节都没改）

先验证"标志位是否被读取方认可"。探针 ISO 只做一件事：把 22 个场内容器的
`BF` 成员改成未压缩存储，**内容就是原来的 `fNNN.bf`，一字未改**。

```
/fld/f/f001/f001_000.LB   21376 -> 31808   BF: compressed 6052 -> raw 16476
/fld/f/f025/f025_000.LB   72320 -> 150848  BF: compressed 37718 -> raw 116236
（共 22 个）
```

已核对：改写后**所有其它成员（INF/NPL/SKY/WAP/AMB）逐字节不变**，
BF 成员内容与散装 `.bf` 完全一致，DDT 无重叠，IMG 记录大小已同步。

**判据**：
- 进任意一个有 NPC 的场地，对话 / 宝箱 / 传送等提示**行为与原来完全一样**
  ⇒ 标志位有效，之后就能直接改场内容器里的台词；
- 该场地**出错、卡死或行为异常** ⇒ 读取方不认这个标志位，得回去解压缩算法。

顺带一提：松装 `.bf` 与成员 `unpacked` 大小**逐一相等**（`f001.bf`=16476、
`f025.bf`=116236…），这本身就强烈说明两者内容相同。

### 11.8 第一个探针崩溃，改用两个隔离探针（2026-09-12）

第一次的 `DDS2_probe_lb.iso` 让游戏**启动后进入 OP 动画时卡死**，
日志是 `pc:00328A20/00328A60` 反复 `TLB Miss addr=0x4/0x8/0xc` —— 空指针死循环，
和当年 AICALC 盲改后的崩溃同一个签名。

排查中发现一个**确定的缺陷**：`DDS3.IMG` 被撑大后声明的大小是
`1467984896`，**不是 2048 的倍数**（原版 `1466599424` 恰好是）。
ISO9660 的"逻辑块"读取方会按扇区截断，最后一个不完整扇区就读不到。
已修：`alloc_extend()` 现在把新大小向上取整到扇区边界。

但崩溃也可能来自另一件事：**读取方可能根本不认"压缩标志 0"**。
所以要一次把两者分开，做了两个内容不同的探针：

| ISO | 改了什么 | 用来回答 |
|---|---|---|
| `DDS2_probe_reloc.iso` | 22 个场内容器**逐字节不变**，只是搬到 IMG 末尾（DDT + IMG 记录同步更新） | 扩容/搬移本身有没有问题 |
| `DDS2_probe_lb.iso` | 同上，并且把 `BF` 成员改成**未压缩存储**（`compflag=0`） | 压缩标志是否被认可 |

判定表：

| reloc | lb | 结论 |
|---|---|---|
| 正常 | 正常 | 方案成立，可以开始改场内台词 |
| 崩溃 | — | 问题在 IMG 扩容 / 文件搬移，与压缩标志无关 |
| 正常 | 崩溃 | 读取方不认标志位，必须回去解压缩算法 |

两个探针都已核对：IMG 大小扇区对齐且与 ISO9660 记录一致、DDT 无重叠、
其它成员逐字节不变、扩容区里的文件都能正确读回。

### 11.9 `reloc` 探针也崩溃 ⇒ 定位到"IMG 扩容"本身（2026-09-12）

`DDS2_probe_reloc.iso`（**内容逐字节不变**，只把 22 个场内容器搬到 IMG 末尾）
同样死在 `pc:00328A20/00328A60` 的 `TLB Miss` 循环。

全盘二进制 diff 确认它与原版**只有三处差异，全部是有意改的**：

| `0x829be` / `0x829c1` | ISO9660 里 `DDS3.IMG` 记录的大小字段（记录位于 `0x829b2`，LE@+10、BE@+14）|

| `0x57b5f800` 起 | 追加到 IMG 末尾的 1.4 MB 数据 |

也就是说**搬移的实现本身是对的**（文件能按新 LBA 正确读回、其它成员逐字节不变、

判定：

### 11.10 ⚠️ 决定性结论：游戏会校验 `DDS3.IMG` 的声明大小（2026-09-12）

`size` 探针 —— **全盘只差 2 个字节**（只把 ISO9660 里 `DDS3.IMG` 的大小字段从
1466599424 改成 1467648000，不搬任何文件、不改 DDT、不加任何数据）——
**同样卡死**。

⇒ **扩容方案彻底不可行。** 在原有文件大小之内做任何改动都可以，
但**不能改变 `DDS3.IMG` 在 ISO9660 里声明的大小**。

推论：`reloc` 探针的崩溃可以由"改了大小"完全解释，所以**在原有 IMG 边界内
搬移文件本身应该是安全的**（尚未单独验证）。

### 11.11 ✅ 块内压缩格式：**已完全解出**（2026-09-12）

用散装 `fNNN.bf` 作**已知明文 oracle**：`.LB` 里 `BF` 成员的内容同时也以散装
`fNNN.bf` 存在，所以每一种候选读法都能立刻对答案，错了当场就看出来，而不会静默错位。

**token 结构**：操作码 = 字节的高 4 位，小参数 = 低 4 位。没有操作数的 token 是**单字节**。

| op | 短形式 | 长形式（低 4 位 == 0 时） |
|---|---|---|
| `0` | `lo` 个字面量 | `[u16 LE 个数]` + 那么多个字面量 |
| `1` | `16 + lo` 个字面量 | — |
| `2` | `lo` 个零字节 | `[u16 LE 个数]` 个零字节 |
| `3` | `16 + lo` 个零字节 | — |
| `4` | 后一字节重复 `lo` 次 | `[u16 LE 个数]` + 填充值字节 |
| `5` | 后一字节重复 `16 + lo` 次 | — |
| `6` | 从 8 位距离回拷 `lo` 字节 | `[u16 LE 长度]` + `u8` 距离 |
| `7` | 从 8 位距离回拷 `16 + lo` 字节 | — |
| `8` | 从 16 位距离回拷 `lo` 字节 | `[u16 LE 长度]` + `u16 LE` 距离 |
| `9` | 从 16 位距离回拷 `16 + lo` 字节 | — |
| `10` | `lo` 组"字节 + 零" | `[u16 LE 组数]` + 那么多个字节 |
| `11` | `16 + lo` 组"字节 + 零" | — |
| `12..15` | **不存在**（在全部 174 个成员中一次也没出现） | |

**统一规律**：凡是基数取 0 的家族（op `0/2/4/6/8/10`），当短形式的长度会算成 0 时，
该操作码就改成长形式 —— 长度变成 `u16`，后面接该家族原本的操作数。基数 16 的兄弟
（`1/3/5/7/9/11`）永远算不出 0，所以没有长形式。

**踩过的七个坑**（每一个都是靠"逐字节吻合前缀长度"在全语料上量出来的）：

1. `op 2` 是**单字节** token。早期把它读成"零个数 + 字面量个数"两个字节，
   前几百字节碰巧也对，随后静默错位。
2. `op 0` 低 4 位为 0 时是**长字面量**，不是"空字面量"。
3. `op 2 / op 4 / op 10` 同理：低 4 位为 0 时是逃逸，不是"什么都不做"。
4. `op 4 / op 5` 是**字节填充**（填充值作为操作数跟在后面），
   **不是** 一开始以为的 `32 + lo` / `48 + lo` 个零字节。`op 4` 在 `f001` 里
   只出现**一次**，而正是解码脱轨的那一处。
5. `op 6 / op 8` 算出长度为 0 时是长回拷。
6. `op 10` 是压缩器存"高字节全为 0 的 u16 表"的方式 —— 这正是 FLW0 的字符串表 /
   操作数表的形态，也是压缩流看起来"少了一半零"的原因。
7. 长形式 `op 8` 的距离是 **16 位**，长形式 `op 6` 的距离是 **8 位**。

**验证结果**：

| 验证 | 结果 |
|---|---|
| 有 `*.bf` 明文 oracle 的 22 个 `BF` 成员 | **22/22 逐字节完全一致**（1 136 745 字节，100.0%）|
| 镜像中**全部** `.LB` 的压缩成员 | **174/174** 解压结果长度 == 头部声明的 `unpacked` |

⚠️ 一个成员细节：`stored` 可以比真实压缩流更长，尾部是零填充，
所以**产够 `unpacked` 字节就停**，不要强求把整个成员读完
（例如 `f001_000.LB:INF` 声明 `stored=111`，实际只用到 94 字节）。

代码：解码 `src/ddstool/lbcmp.py`；编码 `src/ddstool/lbcmp_enc.py`。

### 11.11.1 ✅ 编码器：代价最优解析，`BF` 已能原地写回

`lbcmp_enc.compress_best()` 用**代价最优解析**（动态规划）替代贪心：每种 token 的代价在
长度区间内是常数

| 家族 | 长度 ≤ 31 | 长度 ≥ 32 |
|---|---|---|
| 字面量 | `1 + n` | `3 + n` |
| 零 | `1` | `3` |
| 字节填充 | `2` | `4` |
| "字节 + 零"组 | `1 + k` | `3 + k` |
| 回拷（8 位距离） | `2` | `4` |
| 回拷（16 位距离） | `3` | `5` |

于是每个家族都是"线性项 + 常数"，正向 DP 配滑动最小值即可 **O(n)** 求出最便宜的解析；
只有回拷是非线性的，用匹配器给出每个位置在 8 位 / 16 位距离下的最长匹配。

**结果（29 个 `BF` 成员）**：

| 编码器 | 总字节 | 超过原 `stored` 的成员 |
|---|---|---|
| 原版（retail） | ≈578 KB | — |
| 贪心 `compress()` | 622 087 | **27 / 29**（最差 +3335）|
| `compress_best(chain=32)` | **506 279** | **0 / 29** |
| `compress_best(chain=128)` | 503 185 | 0 / 29 |
| `compress_best(chain=512)` | 502 554 | 0 / 29 |

也就是说最优解析后**每个 `BF` 都比原版小约 12–13%**，原地写回有充足余量。

### 11.11.2 成员布局：`0xFF` 终止符与 64 字节对齐

压缩流后面紧跟一个 **`0xFF` 终止符**；`stored` 字段在零售数据里恒等于
「解码消耗字节数 + 17」，但它**只是信息字段，不决定下一个 chunk 的位置**：

```
下一个 chunk 头 = align64(数据起点 + 解码消耗字节数 + 1)
```

（145 个"后面还有 chunk"的成员里 **144 个**精确吻合；唯一一个例外是
`f012_000.LB:WAP`，它是 64 字节边界的临界情形，加上终止符的 +1 后也吻合。
另外 29 个"文件里最后一个成员"没有下一个 chunk 可对齐。）

**推论（很关键）**：直接把流压短会让**后面所有 chunk 全部错位**。
所以写回时不能简单缩短，必须让终止符落回**原来所在的 64 字节块**。

`lb.replace_packed()` 的做法：

1. 先算出原成员解码真正消耗了多少字节 `used`；
2. 新流长度必须满足 `数据起点 + 新流长度 + 1` 落在原来那个 64 字节块内
   （即 `新流长度 + 1 ∈ (下一个 chunk − 数据起点 − 64, 下一个 chunk − 数据起点]`）；
3. 差额用**零输出 token**（`00 00 00` = op0 长形式、计数 0）补足，
   而且插入在**最后一个 token 之前** —— 只有这样解码器才会真的消耗它们
   （解码器一旦产够 `unpacked` 字节就会停下，追加在末尾的填充根本不会被读）；
4. 头部**一个字节都不动**（`stored` / `unpacked` 保持原值），槽位、终止符位置、
   文件大小、其它成员偏移全部不变。

实测：`/fld/**` 下 **29 个容器、174 个成员全部写回成功，0 个放不下**；
逐个校验 **chunk 偏移完全不变、文件大小不变、解压内容与原内容逐字节相同**
（`selftest.py` 已把这三条作为回归项）。

#### 11.12.1 消息文本的语法：字形 + 控制码

场内消息的文本是**两字节字形**与**控制码**交替的流。字形以 Shift-JIS 风格的首字节开头
（`80`–`9F` / `E0`–`EF`），其余字节都是控制码 —— `0a`（换行）、`00`，以及 `f0`–`ff`
开头的指令。在 1797 条场内消息上验证：这个切分只留下 **58 种不同的控制串**，
而且**每一种要么以 `f0`–`ff` 开头，要么就是换行**：

```
f2 08 ff ff f2 07 07 ff   每条消息固定开头
0a                        换行
0a f1 04 00               消息结尾
f2 02 01 ff / f2 02 05 ff ...
```

#### 11.12.2 为什么不能整条文本直接搬（v27 崩了）

v27 是整条文本互换，实机**台词确实变成了别场次的**（说明容器写回被正确读取），
但**中途卡死**：`TLB Miss addr=0x0/0x1/0x8/0xc/0x14/0x20`（典型的空/野指针，
而且地址都很小，像是在循环里遍历一张指针表）。

原因：消息正文里的**控制码指向本场景的东西**（立绘 / 模型 / 条目号等）。
把带 `f1 xx`、`f2 xx yy ff` 这类码的消息搬到另一个场景，那个场景没有对应资源，
于是取到空指针。

#### 11.12.3 解决办法：控制码留在原位，只把纯文本片段丢进随机池

一条场内消息 = `控制码` 与 `纯文本片段` 交替的流。做法是：

```
f2 08 ff ff f2 07 07 ff | 80 9e 87 da 84 e4 | 0a f1 04 00
^^^^^^^^^^^^^^^^^^^^^^^   ^^^^^^^^^^^^^^^^^    ^^^^^^^^^^^
控制码：原样不动           纯文本片段：随机     控制码：原样不动
```

* **控制码一个字节都不动** —— 它们指向本场景的立绘 / 模型 / 条目号，动它们就会崩。
* **纯文本片段**（字形游程）按**字节长度**丢进**全游戏**随机池互换。
* 片段长度相同 ⇒ 消息长度不变、条目长度不变、文件长度不变。
* 片段长度为偶数（整数个双字节字形）⇒ 交换永远不会把一个字形劈开。
* 池内排序做**跨文件优先**（`_round_robin`），因为"来自别的场景"才是随机感的关键。

##### 空格字形也要隔离（v30）

只在"控制码 vs 文本"上做隔离还不够：**空格字形 `80 80` 本身会被当成文本片段**。
它是池里最常见的孤立片段（105 个，另有 88 个 `80 80 80 80`），而且总是紧跟在
`0a f1 04` 页分隔码后面：

```
0a f1 04 80 80 f2 08 ff ff <下一页的文本>
         ^^^^^ 这里是空格 / 页分隔，不是台词
```

把它当文本换走，那一页就**变成空行**（v29 实机现象）。
所以 `80 80` 被归入**受保护字节**：原地不动，也永远不进池。
实现上要注意**仍然按两个字节推进**，否则会把后面那个字节误当成 trail。

| 整条文本 + 控制码字节数配对（v28） | 1392/1797 条 | 696 | 实测 647/731 |

#### 11.13.1 CG 字幕：等长互换，而且只有文字会动

条目的布局（§11.4）：

```
+0      char[16] 名字
+16     u8[8]    reserved
+24     u16      行数 n
+26     u16      0xffff
+28     u32      语音/时间[n]
+28+4n  u32      文本长度
+32+4n  u8[]     文本
```

槽位容量不是问题：条目占多少字节由**下一张表项**决定，所以文本能长到
`cap = size - (32 + 4n)`；1379 条实测文本总量 52 481 字节，`cap - length` 之和
**10 831 字节（20.6%）**。

**变长：不行（实机 2026-10-06）。** 做了一个干净实验（不按长度分组、给每条字幕挑一个装得下的
文本、槽位剩余补 0 并更新 `length`、名字/reserved/行数/`0xffff`/语音数组一字节不动，
自检全绿）—— 实机结果是部分 CG 完全没字幕、有字幕的时机对不上且很快消失。
所以 **CG 字幕一律保持原字节长度**。

##### 控制码是每段过场专属的

CG 文本不是"前缀 + 正文"，而是**每段过场专属的控制码包着正文**（`.` 表示一个字形）：

```
e601_001   f208ffff f207                  . 0a f214 XX 01 00
e603_001   f208ffff f41305ffdb08 f207     . 0a f215 00 00 00
e603_001   f208ffff f41306ffdc08 f207     . 0a f215 00 00 00
```

93 个 `.PM1` 有 **334 种不同前导码**，**36 个文件连自己内部都不共享同一个**，结尾码也不一样。
把**整条文本**（连控制码）发给另一段过场，接收方就拿到一个不认识的 `f413 …` 块 ——
实机表现正是"字幕偏晚、停留时长不对、有些干脆不显示"。**和长度无关。**

所以 CG 采用**和场内对话完全相同的原则**：把文本切成"控制码 / 纯文字游程"，
**控制码一个字节都不动**，只有纯文字游程参与互换（**等长**）。副产品是每条字幕的 `0a`
结构也不变，所以显示形状和零售一致。

##### 两个把我坑了很久的细节

**① 开头的 `81ff` 是标记，不是文字。** 文本真实布局是
`f208fffff207` + `81ff` + 正文。证据：1379 个条目里 **1373 个正好出现一次**，
永远在正文最开头（第二条 `0a` 行不会再有）；69% 的 CG 游程以它开头，
而 4533 个场内游程里**只有 2 个**。`0x81` 是 Shift-JIS 前导字节，所以掩码把它并进第一个游程 ——
只要替身池**只含 CG 游程**（它们几乎都以 `81ff` 开头）它就"顺带"被保留；
一旦把场内游程放进替身池，标记就被换掉，字幕整段失效。

**② 控制码的操作数会被误当成字形（这才是真正的元凶）。**

```
零售  f208ffff f41305ff e608 f207  <正文>
      └────────────────┘ 这是控制码，e6 08 是它的操作数
旧版  f208ffff f41305ff 81ff f207  <正文>
                        └──┘ 操作数被当成 2 字节字形游程，换掉了
```

掩码把 `0x80–0x9F` 和 `0xE0–0xEF` 当前导字节，而**操作数正好可能落在这个范围**。
控制码块被改坏后，这条字幕显示不出来；语音是按条目名挂在字幕上的，字幕一坏语音也不播；
**后面整个过场就一起停了** —— 这就是实机反复出现的"前几句正常、之后既没字幕也没语音"。

修法：**长度不足 `MIN_SWAP_RUN = 4` 字节的游程一律固定**。操作数都是短的，正文都是长的。

逐字节对照（检查"掩码判定为固定的字节里有多少被改写"）：

| 构建 | CG 文本改动数 | 固定字节被改写 |
|---|---|---|
| 修复前 | 1293 | **196** |
| 修复后 | 1261 | **0** |
| `cg_off`（完全不改） | 0 | 0 |

**这一条不是新引入的**：修复前的所有版本都有，只是哪一段被撞上取决于种子和替身池，
所以时好时坏、看起来像随机。

#### 11.13.2 场内对话：可以，而且不用碰压缩层

场内消息在 `.bf` 的 MSG1 块里（§11.12）。块结构是"表 + 条目"：

```
+0      "MSG1"
+8      u32 block_size        ← 块的总大小
+24     表：{ u32 flag; u32 rel_offset; } × N   （rel 相对表起点）
之后    条目，按表顺序连续摆放
```

**关键点：块的大小是块自己声明的，条目在块内部的排布完全自由。**
只要新排布不超出块尾，就可以原地重排，`block_size` 不变 ⇒ `.bf` 大小不变 ⇒
压缩成员 `unpacked` 不变 ⇒ `lb.replace_packed` 原样可用（连压缩都不用重新算）。

空间也够（实测 65 个块、3263 条）：

| 指标 | 数值 |
|---|---|
| 文本总量 | 177 220 字节 |
| 条目之间的空隙 | 24 663 字节 |
| 块尾剩余空间 | 67 127 字节 |
| **合计可增长** | **91 790 字节 = 51.8%** |

做法（`--field-varlen` / GUI「允许不同长度的场内对话互换」）：

1. 按 §11.12 把每条消息切成"控制码 / 纯文本游程"，控制码原地不动；
2. 每个纯文本游程从**全游戏池**里挑一个替身，**长度任意**（优先跨场景）；
3. 每个块有一个文本字节预算（`块尾 - 表尾 - 所有头部`），替身只允许在预算内变长，
   变短还能把预算还给后面的消息；
4. 每个游程还受**行宽**限制（见下），任何一行不得超过 `FIELD_MAX_LINE`；
5. 整块用 `msgtbl.rebuild_block` 重新排布：条目首尾相接、表里的 `rel_offset` 全部更新、
   块尾补 0；**块大小不变**；
6. 预算仍然不够的块退回到**等长互换**（实测 65 个块里 4 个），所以不会有块被白白跳过。

**引擎认的是长度字段，不是 `00` 结尾。** 这是"变长到底安不安全"的关键证据：
零售数据里 3220 个场内条目中，**880 个条目在声明的文本长度之后紧接着就是非零字节**
（紧跟着下一条目的 `name[16]`），还有 **228 个条目文本末尾和下一条目之间一个空隙都没有**。

| 指标（零售 64 个场内文件，3220 条） | 数值 |
|---|---|
| 最后一个文本字节是 `00` | 3118 |
| 文本结束到下一条目开头**没有空隙** | 228 |
| 文本结束后**第一个字节不是 `00`** | 880 |
| 文本末尾到下一条目的最大空隙 | 398 字节 |

如果引擎是"扫到 `00` 为止"，这 880 条会直接读进下一条目的名字里、显示出乱码 ——
实机上显然不会，所以**引擎必须用 `+28+4×lines` 处的 `u32` 长度字段定界**。
`rebuild_block` 每次都把这个字段更新成新文本的长度，所以换长文本在读取层面是安全的。

消息末尾的 `00`（如果有）属于控制字节，`field_mask` 把它标成"不可移动"，
自检里的"控制码序列逐字节不变"同时覆盖了它。改完之后"最后一个文本字节是 `00`"
的条目数 **3118 → 3118，完全没变**。

**行宽上限：对话框不自动换行，所以不能顶出去。** 场内消息用 `0a` 手动分行、
`f1 04` 翻页；把 1908 条场内消息按 `0a` 切开共 6249 行，可见字形格数分布是：

| 行宽（格） | 累计占比 |
|---|---|
| ≤ 12 | 75.6% |
| ≤ 20 | 97.9% |
| ≤ 24 | 99.5% |
| ≤ 33 | 100%（全游戏只有 4 行到 33） |

也就是说**文本作者从来不让一行超过 33 格**，这正是对话框的容量。
变长互换如果不管这一点，很容易把某一行顶到 40 格以上而显示不下，
所以 `textdata.FIELD_MAX_LINE = 33`：`_line_cells()` 给出每个游程所在行的
"其余部分占多少格"，`pick()` 把候选的长度同时夹在 `FIELD_MAX_LINE - 其余格数` 之内。
同一行有多个游程时，已经变长的部分也会从后面的预算里扣掉。
实测被这个上限挡下来的候选有 4401 次（seed 11），换手总数不变，
**改完之后全场最宽的一行仍然是 33 格**。

**块尾必须夹到 `.data.msg` 段的末尾。** 实测有 27 个块自己声明的 `block_size` 越过了
`.data.msg` 段尾 2 个字节（例如 `/event/e800/e802/scr/e802.bf`：块声明到 `0x47C`，
但后面的 `.data.str` 从 `0x47A` 开始；`e803.bf` 是 `0x4CC` / `0x4CA`）。
如果按块自己声明的末尾去补 0，就会把后一个段开头的字节抹掉 —— 这正是初版
`--field-varlen` 在探针 ISO 里改坏 2 个文件的原因。现在 `msgtbl.block_bounds` /
`rebuild_block` 接受一个 `limit`（`textdata._msg_section_limit` 从 FLW0 段表算出
`start + unitSize × unitCount`），块尾取两者的较小值；补 0 也只补到**原排布的实际末尾**
（各条目 `+32+4×lines+声明长度` 的最大值），绝不越过块尾或文件尾。

自检逐字节验证（`selftest.py`）：文件大小不变、改动**只发生在 `.data.msg` 段内**、
**控制码序列逐字节不变**、**名字/标志/语音数组（`+0 .. +28+4×lines`）逐字节不变**、
每个游程都是整数个字形、**没有一行超过 33 格**、宽度上限确实起了作用、
零售数据确实是长度定界、`.LB` 只改了 `BF` 成员且大小不变。

实测（seed 11）：4435 个游程被换掉，其中 1812 条消息的长度发生变化，重排 64 个块、
4 个块回退到等长；22 个场内容器全部写回成功（0 个放不下）；27 个越界块全部被夹住，
0 个文件在段外被改动；行宽上限拦下 4401 个候选，最宽行仍是 33 格。

## 12. 曼斗罗（Mantra）技能组 + 属性奖励随机（2026-09-13 定稿）

### 12.1 曼斗罗的数据拆成两份，而且不在同一个文件里

| 数据 | 位置 | 内容 |
|---|---|---|
| 六边形网格 | `/facility/data/mtrMantraBlockData.tbl`（在 `DDS3.IMG` 里） | 176 条 × 32 字节：`flag`(rank<<4\|type)、`id`、网格坐标 `A/B`、6 个邻居 |
| **消耗 + 属性奖励 + 技能组** | `SLPM_657.95`（**ISO9660 根目录，不在 `DDS3.IMG` 里**） | 176 条 × 36 字节，偏移 `0x301388`，按 `id` 索引 |

`mtrMantraBlockData.tbl` 的 32 字节记录：

```
+0x00 u16 flag      (rank << 4) | type      type 1..4，rank 0..3，bit8 = 剧情曼斗罗
+0x02 u16 id        上表的索引
+0x04 u16 A         col*10 + 5*(row&1)      六边形 odd-r 布局
+0x06 u16 B         row*10
+0x08 u32 邻居[6]   记录 id * 32，0 = 无；方向对为 (0,3) (1,4) (2,5)，关系对称
```

**这个文件里既没有技能也没有属性奖励**。邻居字段是 6 个方向的图（`.data 0x1624` 起的第二段就是
这些字段的指针表，条目数 456 = 2 × 228，正好等于非零邻居数）。

`SLPM_657.95` 里的 36 字节记录（**技能和属性奖励都在这里**）：

```
+0x00 u32 消耗（Karma，100 ~ 200000）
+0x04 u8  属性奖励[5]   STR / MAG / VIT / AGI / LUK，各 1 字节
+0x09 u8  0
+0x0A u16 技能 id[8]    0 结尾，最多 8 个
+0x1A u16 0
+0x1C u16 0 / 1         （只在 50 Karma 的填充记录上为 1）
+0x20 u16 组号（网格列号，1..7）
+0x22 u16 1
```

**属性奖励只有 8 条记录非零**：就是 8 个剧情曼斗罗 145..152（它们在网格数据里 `flag & 0x100`）。
每条提升一个属性 1~3 点，而 151 号是「五维各 +1」——所以这 5 个字节确实是五个属性、一字节一个：

| id | 奖励 |
|---|---|
| 145 | VIT+2 |
| 146 | STR+2 |
| 147 | AGI+3 |
| 148 | MAG+3 |
| 149 | LUK+3 |
| 150 | VIT+3 |
| 151 | STR+1 MAG+1 VIT+1 AGI+1 LUK+1 |
| 152 | STR+3 |

其余 168 条记录的这 5 个字节全是 0，这正好对应需求里的「部分曼斗罗」。

### 12.3 随机方式

**技能组（需求 1）**：默认 `--mantra-mode skills`（**打散重发**）：

* 把所有**会教技能**的曼斗罗（当前 107 个、共 267 个技能槽）的技能全部丢进一个池子；
* 洗牌后按「每个曼斗罗原本有几个技能」重新发下去 ——
  **每个曼斗罗的技能数量不变**（网格权重、消耗的含义都不变），
  但技能来自全图各处，而不是「A 的一整套原封不动给 B」；
* 发完后有一个修复过程（`_avoid_own_skills`）：任何拿回自己技能的曼斗罗都会和别处换掉，
  保证 **0 个曼斗罗保留自己的技能**；
* 池子只是被置换，所以技能总量不变；
* 实测：107/107 个曼斗罗的技能列表都变了，没有一个新列表等于任何一条原有列表，
  平均每个技能列表来自 **2.48 个**不同的原始曼斗罗（旧模式这个值是 1.0）。

`--mantra-mode sets` 保留旧的**整组互换**：节点保留网格位置、rank/type、消耗和属性奖励，
只把整个技能列表跟另一个节点 1:1 交换（技能数量可以不同，字段固定 8 槽、0 结尾）。
两种模式在自检里都有覆盖。

**属性奖励（需求 2）**：把 8 个剧情曼斗罗的**五维向量**在它们之间整体置换：

* 节点保留自己的位置、消耗和技能；
* 只在有奖励的节点之间交换，所以「哪 8 个节点给奖励」不变，只是奖励换了主人；
* 点数总量不变（当前 24 点）。

`--mantra-costs` 可以额外把消耗也一起置换。

### 12.5 需求 3（角色初始技能组）：游戏自己会重算，不需要改数据

需求 3 是「对初始就习得了部分曼斗罗的角色，修改其初始技能组」。逆向的结论是
**这份「初始技能组」在镜像里并不存在，游戏每次都会用曼斗罗表重新推导**：

1. 新游戏 / 换章节入口 `0x118598`：把玩家数据整块清掉
   （`0x11ab38` 对 5 个角色各 `memset 452` 字节），
   然后依次调用 `0x313370`、`0x313930`、`0x11c998`、`0x11ca28`、`0x11d438`；
2. `0x313930` 逐角色、逐曼斗罗槽调用 `0x3137f8`（应用曼斗罗）；
3. `0x3137f8` → `0x314ab8`（取该曼斗罗的技能列表）→ `0x313f98`（写技能位图）。

也就是说：**技能位图唯一的来源就是曼斗罗表**（所有 `0x313f98` 的调用点传的都是曼斗罗 id），
所以曼斗罗表一改，角色（包括一开始就带着曼斗罗的角色）的技能组在游戏内会自动跟着变，
镜像里没有任何「初始技能」清单需要同步。自检里因此没有对应的写回检查。

顺带：`0x4F`/`0x45`（曼斗罗 75 / 69）是给 1/2 号角色的剧情锁定节点，见 `0x290ca0`。

## 13. 主人公恶魔形态模型替换：伐楼罗 → 黑伐楼罗（2026-09-14，待实机验证）

目标：把主人公（萨弗）变身时用的**伐楼罗**（Varuna）模型，换成游戏里实际出现的
**黑伐楼罗**（kuro_varuna）模型。这是纯外观替换，不涉及任何数值。

### 13.1 角色槽位 → 模型文件

角色（人类形态）与「阿特玛形态」是两张并行的模型表，都在 `SLPM_657.95` 的 `.data` 里：

| 表 | 虚拟地址（VA） | 表项 | 指向 |
|---|---|---|---|
| `human/pcNNN.PB` | `0x3C1BEC` | 48 条，步长 12 | 第 i 条 → `human/pcNNN.PB`（NNN = i） |
| `human/pcNNN_on.PB` | `0x3C2EAC` | 32 条，步长 12 | 第 i 条 → `human/pcNNN_on.PB` |
| `devil/NNN.PB` | `0x3C1E2C` | 352 条 | 第 i 条 → `devil/NNN.PB` |
| `on/NNN_on.PB` | `0x3C303C` | — | 第 i 条 → `on/NNN_on.PB` |

（ELF：VA = 文件偏移 + `0xFF000`；文件名串紧挨着表，按 id 递减排列。）

第 `0x11` 条解析出来是：

* `/model/human/pc011.PB` = 1 272 064 字节
* `/model/human/pc011_on.PB` = 1 232 000 字节

### 13.2 为什么 `pc011` 就是伐楼罗

`.PB` 模型把节点名当**明文串**存在文件里，所以模型是「自带铭牌」的：

| 模型 | 根节点 | 身体节点 |
|---|---|---|
| `/model/human/pc011.PB` / `pc011_on.PB` | `x101_root` | `varna_body` |
| `/model/devil/12A.PB` | `x101_root` | `varna_body` |
| `/model/devil/10E.PB` | （无） | `varna_body` |
| `/model/devil/10F.PB` | （无） | `varna_body01` |

对照组：`pc001.PB` 是 `surf_body`／`surf_face`（萨弗本人），`pc002` 是 `sera_*`，
`pc003` 是 `heat_*`，`pc004` 是 `aljira_*`（阿尔吉拉），`pc005` 是 `gale_*`……
即 `pc0NN` 是队友的人类形态，`pc01N` 是他们的阿特玛形态，`0x11` 正好落在萨弗的
阿特玛槽上，节点名又是 `varna_body` —— **`pc011[_on].PB` 就是伐楼罗**。
（`devil/12A.PB` 是同一只「普通伐楼罗」，只是贴图分辨率更低。）

### 13.3 `.PB` 模型的文件结构

`.PB` 是一串**扁平块**，每块 8 字节前缀 + 4 字节 magic，`size` **包含**这 8 字节前缀：

```
[u32 type][u32 size]['PIB0'|'TXP0'|'MD00'|'MT00'|'END0'] payload
```

块与块之间补零到 **0x40 对齐**（`PIB0` 588 字节 → 下一块正好在 0x280）。
`TXP0` 自己还是个容器：小表 + 每张贴图一个 `TMX0` 子块。

| 文件 | `PIB0` | `TXP0` | `MD00` | `MT00` |
|---|---|---|---|---|
| `/model/human/pc011.PB` | 588 | **199 936** | 307 058 | 764 316 |
| `/model/human/pc011_on.PB` | 588 | **199 936** | 260 862 | 770 464 |
| `/model/devil/12A.PB`（普通伐楼罗，低模） | 204 | 15 616 | 249 752 | 351 558 |
| e639 `kuro_varuna.PB` | 36 | **199 936** | 274 128 | 38 772 |
| e639 `siro_varna.PB` | 36 | **199 936** | 286 696 | 13 007 |

关键：`pc011`、`pc011_on`、`kuro_varuna`、`siro_varna` 的 **`TXP0` 块（199 936 字节）
头部和表完全逐字节相同**（3 张贴图，相对偏移 0x40 / 0x10480 / 0x208C0，
全部 256×256、格式 19、1024 字节调色板）。

### 13.4 黑伐楼罗的贴图在哪里

事件包 `/event/e630/e639/e639_001/E639_001.PM1` 开头是一张 **32 字节一项的模型名表**，
后面每个名字跟一个 `PIB0` 模型块，顺序一一对应（名字表第 8 项起才是 `.PB`）：

```
heat_ori @0x035A60 (836672)  himo @0x101EA0 (565312)   m_surf @0x18BEE0 (716544)
madam @0x23ADE0 (527424)     schro @0x2BBA20 (269312)  siro_varna @0x2FD620 (499840)
surf @0x3776A0 (1022848)     surf_ori @0x471220 (843968) kuro_varuna @0x53F2E0 (513024)
aguni @0x5BC6E0 (348928)     surf_artoma_all @0x6119E0 (568000) dead_stage @0x69C4A0 (1660576)
```

调色板均值（1024 字节 / 256 项，取 RGB 平均）：

| 贴图块 | 贴图 1 | 贴图 2 | 贴图 3 | 合计 |
|---|---|---|---|---|
| `pc011_on`（伐楼罗） | 392 | 157 | 531 | **1080** |
| e639 `kuro_varuna`（黑） | 478 | 94 | 181 | **753** |
| e639 `siro_varna`（白） | 549 | 404 | 336 | 1289 |
| `/model/devil/10E.PB`@`0x3B040` | 478 | 94 | 181 | **753** |

`kuro_varuna` 明显更暗 —— 这就是「黑」的来源。

`/model/devil/10E.PB` 与 `/model/devil/10F.PB` **不是**那种形状的模型容器
（它们的块链在 `PIB0` 之后就断了），但各自**内嵌了一份完整的贴图块**：

* `10E` @ 文件偏移 `0x3B040`，199 936 字节，与 e639 `kuro_varuna` 的 `TXP0` 逐字节相同；
* `10F` @ 文件偏移 `0x1D340`，与 e639 `siro_varna` 的 `TXP0` 逐字节相同。

（最初用「最长公共子串」比对时看到 199 970 字节相同，就是这一段。）

### 13.5 做法：只换 `TXP0` 块（**不是**整文件替换）

⚠️ **先走过的弯路**：第一版把 `/model/devil/10E.PB` 整个文件覆盖进两个槽位
（`10E` 比槽位小，补零到原大小）。结果**实机变身时加载模型直接卡死** ——
因为 `10E` 根本不是合法的 `human/pcNNN_on` 模型容器。

现在改成**外科手术式替换**：只把目标文件里那一个 199 936 字节的 `TXP0` 块换成
`10E`@`0x3B040` 的对应块，其它一个字节都不动：

```
pc011.PB     : [PIB0 588][TXP0 ← 换掉][MD00 307058][MT00 764316][END0]
pc011_on.PB  : [PIB0 588][TXP0 ← 换掉][MD00 260862][MT00 770464][END0]
```

骨架（`PIB0`，含 `x101_root`）、网格（`MD00`）、材质/动作（`MT00`）、`END0`
以及所有偏移全部保持原样，文件大小不变。因此 `DDS3.DDT` 索引不动、
`DDS3.IMG` 一个字节都不偏移。

### 13.6 不变量（自检逐字节验证）

| 不变量 | 实测 |
|---|---|
| 两个槽位都带 `varna_body` 节点 | ✅ |
| 两个槽位的 `TXP0` 都是 199 936 字节，且表头逐字节相同 | ✅ |
| 供体贴图块是**更暗**的那一套 | ✅ 调色板均值 251 < 360×0.8 |
| 供体块确实等于 e639 `kuro_varuna` 的 `TXP0` | ✅ 199 936 字节完全相同 |
| 目标文件大小不变 | ✅ 1 272 064 / 1 232 000 |
| 只有 `TXP0` 块内的字节变化 | ✅ 其余部分逐字节相同，`TXP0` 表头原样 |
| 不碰任何其它文件 | ✅ 只写这两个 |
| 默认关闭 | ✅ `Config().black_varuna is False` |

### 13.7 已知风险 / 待实机验证

* 贴图换了，但**材质/顶点色**（`MT00`）仍是伐楼罗自己的。如果「黑」还带材质参数，
  这次替换可能只变暗一部分 —— 只能实机看。
* `/model/field/player_b.PB`（场上形态，554 176 字节）的 `TXP0` 也是同一套
  199 936 字节，**理论上也能这样换**；本层先不动它。
* 该层**默认关闭**：命令行 `--black-varuna`（或 `--only models`）开启，
  GUI 在「文本与语音」页有开关（默认不勾选）。
