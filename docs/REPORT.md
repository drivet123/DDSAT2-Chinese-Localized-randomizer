# 逆向分析与实现报告 (DDS2 Randomizer)

本文件记录工具用到的所有文件格式、推导依据与置信度，供后续维护。

## 1. 光盘容器 (已验证，置信度 100%)

* 标准 ISO9660，2048 字节扇区。
* 根目录两个数据包：
  * `DDS3.DDT` (LBA 2332, 167233 字节) —— 文件索引。
  * `DDS3.IMG` (LBA 2414, 1 466 599 424 字节) —— 数据本体。

### DDS3.DDT

广度优先序列化的 12 字节记录树：

```
struct Entry { u32 name_off; u32 lba; s32 size; };
```

* 文件：`lba` 是 IMG 内的扇区偏移，`size` 是字节数。
* 目录：`lba` 是子记录数组在 DDT 内的偏移，`size` 为负数，绝对值等于子项数。
* 根记录在 0x00，随后根的子记录数组，再按层写入「名字字符串 + 子记录数组」。

解析结果：493 个目录 / 6642 个文件，扇区对齐，无重叠；全部文件总大小
1 459 091 579 字节，IMG 剩余空洞约 7.5 MB。

**结论：所有修改都在原槽位内原地写入（不足补 0），DDT 与 ISO 目录无需重建。**

## 2. /battle/UNIT.TBL (高置信度)

`16 字节头 + 896 × 76 字节记录`（76 字节周期自相关 0.884；占位记录的默认
属性出现在 记录+64，反推 base=16）。

字段（小端）：

| 偏移 | 类型 | 含义 | 依据 |
|------|------|------|------|
| 0..9 | u16×5 | 技能 id（0=空） | 取值 ≤571，分布随槽位递减 |
| 12 | u16 | HP | 占位记录为 0xFFFF；与 MP 比值符合常规 |
| 16 | u16 | MP | |
| 64..68 | u8×5 | STR/MAG/VIT/AGI/LUK | 占位记录固定为 28,28,28,23,14；最大 99 |
| 69 | u8 | 类型/标志 | |
| 72..75 | u16×2 | 另外两个技能 id | |

记录区段（按内容分类）：

* 0..126：非单位数据（属性/抗性表）。
* 128..511：**单位本体**（其中 242..382 为占位空槽）。
* 512..895：抗性表（u16 数值 + u16 标志；100 = 普通）。

## 3. 敌人 id ↔ 单位记录 (高置信度)

`ENCOUNT.TBL` 里的敌人 id **N 对应 UNIT.TBL 记录 N + 128**。
把表 1 中出现的所有 id 逐一验证，1010/1040 (97%) 落在合法单位上，且最早
的遭遇战使用的 id (96/60/76/42/33…) 对应最弱的单位 (HP 50..150)，与流程
顺序一致。

## 4. /battle/ENCOUNT.TBL (高置信度)

文件分成两张表：

* 头部 u32 = `0xa000`，即表 1 的字节长度。
* 表 1：1024 条 × 40 字节 —— **遭遇组**。敌人 id 位于偏移 10/12/14/16/18
  的 5 个 u16 槽（0 = 空）。周期性 40 的自相关 0.965。
* 表 2：5960 条 × 12 字节 —— 另一张表（未改动）。周期性 12 的自相关 0.915。

## 5. 台词 / 消息 (高置信度)

斗技场脚本、事件 `.PM1/.PM2/.PM3`、`.bf`、`.bmd`、`.tbl` 共 445 个文件里
含有 **MSG1** 消息块（共 142 个文件、约 3700 条消息）。

单条消息：

```
char name[16];      // 例如 "XSER2010"
u8   reserved[8];   // 0
u16  flag;          // 通常 1
u16  sentinel;      // 0xFFFF
u32  data_offset;   // 语音/附加数据偏移（不透明）
u32  length;        // 文本字节数
u8   text[length];  // 自定义双字节字形编码，4 字节对齐
```

汉化版使用自定义字形编码（非 Shift-JIS/GBK），所以工具把文本当作**不透明
字节串**处理。

洗牌策略：**只交换长度完全相同的文本负载**，原地写入。容器结构、偏移、
文件大小全部不变，因此不可能破坏格式。

## 6. 语音 (高置信度) 与字幕绑定

`/voice` 下 432 个 `.ADB`，每个文件是一条完整的 Sony APCM 4bit ADPCM 流：

```
0x00  32 字节头: u32 版本(0x0b), u32 0, "APCM", u32 0,
                u32 length, 0x100, 0xffffffff, 0x100
0x20  负载, 每 16 字节一个 APCM block (28 samples)
       block0 前导静音; 中间为语音; 倒数第二个 byte1==0x01;
       之后是 stop/end 标记; 其余补 0 到文件末尾
```

文件中**没有**内部分段表，文件本身就是一段语音；消息表里的
`data_offset` 都很小 (<2 KB)。

洗牌策略（`src/ddstool/voice.py`，完整 APCM 解析器）：
* 保留每个文件自己的 32 字节头与 stop/end 尾标记；
* 只在文件之间置换 **音频负载区**，按 16 字节 block 对齐，短则补 0、
  长则按 block 截断；
* 因此每个文件的字节数严格不变，DDT 无需改动，容器不可能损坏。

### 字幕与语音的绑定（默认做法）

MSG1 的每个条目自身就带有「名字 + 语音引用 + 文本」，而语音文件名由条目
名字推导（`X<角色><场景>` ↔ `N<角色><场景>.ADB`，`data_offset` 为片段偏移）。
因此**整体搬运条目**就能把字幕和语音绑在一起换。默认不再单独乱序 `.ADB`
文件（那会破坏绑定）；需要额外混乱时用 `--chaos-voice`。

## 7. AI / 等级

* 敌人 AI 数据在 `/battle/AICALC.TBL`（前 384 条 × 348 字节，偏移 0 处
  存放参数）。若要精确交换 AI 需要进一步解析，目前**保持原样**，符合
  「BOSS 脚本与 AI 不变」的要求。
* 未在 UNIT.TBL 中找到独立「等级」字段（对 HP 做相关性搜索无结果）。
  DDS2 敌人的等级可能并非独立存储。工具以 HP + 属性总和作为强度指标。

## 8. 随机化策略总结

| 层 | 做法 | 强度控制 |
|----|------|----------|
| 普通遭遇 | 只在**出现≥2 次**的 id 里换，且目标模型文件存在 | 新 id 的 HP 与属性总和落在原 id ±tol 内 |
| 含剧情战斗的记录 | **整条跳过** | - |
| BOSS / 剧情战斗 | 把**全局只出现一次**的敌人 id 在各自槽位间互换（不换单位记录） | 按该槽位原 BOSS 的 HP/MP/属性总和精确重设 |
| CG 台词+语音 | **文件内**交换条目正文（保留名字） | 槽位大小不变 |
| 游戏内台词 | 同上，并排除系统提示条目 | 槽位大小不变 |
| 系统文本 | **不动** | - |

### 为什么不能换 UNIT 记录 / 不能随意换 id（重要教训）

* 敌人的 3D 模型是 `devil/<敌人id>.PB`。把遭遇里的 id 换成**没有模型文件**的
  id（例如把 453 个「合法单位」都当作候选）会让战斗在加载模型时**卡死**，
  表现就是「没有敌人也没有玩家模型」。现在候选池严格限定为**遭遇表里已经
  出现过的 id**（全部 174 个都有模型文件）。
* 直接置换 UNIT 记录会让模型与记录里的动作/技能引用不匹配，攻击时卡死。
  现在改为置换**敌人 id**，模型/动作/技能/数值始终来自同一个 id。
* MSG1 条目里的语音偏移在**同一文件内**按条目大小递增（例如 E601_001：
  188→240→308→396…，差值正好等于各条目 size），说明语音/口型是**该文件
  内部按条目顺序排列的流**。因此把整条条目搬到别的文件（或搬走名字）会让
  偏移错位 —— 表现就是 CG 没字幕并卡死。正确做法是**同文件内交换条目
  正文、保留名字**。
* 名字是脚本查找对话的键（例如 `GEIRU_AYAAHIMU` 同时出现在 `f024.bf` 和
  `f024_000.LB`），所以名字必须留在原位。
* 构建工具原来自动把输出改写成 `xxx_1.iso`，导致测试到旧文件。现在若目标
  被占用会**直接报错**，并在写完后回读校验补丁是否落盘。

## 9. 剧情战斗的识别（重要修正）

`/event/**/*.be`（BE 战斗事件脚本）头部 0x50 处存着该战斗对应的**遭遇记录
编号**，并重复出现在 `eNNN_<编号>.BED` 资源名里。扫描全部 33 个 `.be` 得到
编号集合 `{3, 50..64, 80..83, 94..100}`，这些就是剧情战斗记录。
例如 51 号记录 = `[41,40,41]`，正是第一场 BOSS「两个安德拉斯 + 一个ヴェータラ」。

BOSS 随机化 = 在这些记录之间**互换敌人组合（保持敌人数量）**，再按原组合的
HP / 属性总和给新敌人做倍率补偿；脚本与 AI 不动。

台词机制最终确认为（与第一版一致、已在实机验证）：**只交换等长文本负载，
其余字节完全不动**；同文件内的成对交换额外交换语音偏移，使语音跟随字幕。

置信度：容器/ENCOUNT/UNIT/模型约束 高；剧情战斗编号（.be 头部）高；
台词机制 高；语音文件内绑定 高；AI/等级 未解析。
